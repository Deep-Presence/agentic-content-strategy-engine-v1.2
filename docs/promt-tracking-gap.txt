2a. New Repository Method — Batch Prompt Metrics
The key insight: COALESCE(r.parent_prompt_id, r.prompt_id) maps both parent responses and fanout responses to the parent prompt ID. This lets us aggregate a prompt's entire topic performance in one GROUP BY.


async def get_prompt_metrics_batch(
    self,
    company_id: str,
    current_start: datetime,
    current_end: datetime,
    prev_start: datetime,
    prev_end: datetime,
) -> list[Row]:
    """
    Returns per-parent-prompt aggregated metrics in TWO time windows.
    Single query with CTEs — no N+1.
    """
The SQL uses three CTEs:

CTE 1 — Current period metrics:


WITH current_metrics AS (
    SELECT 
        COALESCE(r.parent_prompt_id, r.prompt_id) AS root_id,
        COUNT(*) AS total,
        COUNT(*) FILTER (WHERE r.brand_mentioned) AS mentioned,
        COUNT(*) FILTER (WHERE jsonb_array_length(r.citations) > 0) AS cited
    FROM daily_run_responses r
    JOIN daily_runs dr ON r.run_id = dr.id
    WHERE dr.company_id = :company_id
      AND r.created_at >= :current_start
      AND r.created_at < :current_end
    GROUP BY COALESCE(r.parent_prompt_id, r.prompt_id)
)
CTE 2 — Previous period metrics (identical structure, different time window — for delta computation).

CTE 3 — Daily volume (for sparkline):


daily_volume AS (
    SELECT 
        COALESCE(r.parent_prompt_id, r.prompt_id) AS root_id,
        (r.created_at AT TIME ZONE 'UTC')::date AS day,
        COUNT(*) AS cnt
    FROM daily_run_responses r
    JOIN daily_runs dr ON r.run_id = dr.id
    WHERE dr.company_id = :company_id
      AND r.created_at >= :current_start
      AND r.created_at < :current_end
    GROUP BY COALESCE(r.parent_prompt_id, r.prompt_id), day
)
Main query joins prompts with all three CTEs + a fanout count subquery:


SELECT 
    p.*,
    -- Metrics
    COALESCE(cm.mentioned::float / NULLIF(cm.total, 0), 0) AS mention_rate,
    COALESCE(cm.cited::float / NULLIF(cm.total, 0), 0) AS citation_rate,
    -- Deltas
    COALESCE(cm.mentioned::float / NULLIF(cm.total, 0), 0) 
      - COALESCE(pm.mentioned::float / NULLIF(pm.total, 0), 0) AS mention_delta,
    COALESCE(cm.cited::float / NULLIF(cm.total, 0), 0) 
      - COALESCE(pm.cited::float / NULLIF(pm.total, 0), 0) AS citation_delta,
    -- Fanout count
    COALESCE(fc.cnt, 0) AS fanout_count,
    cm.total AS total_responses
FROM tracked_prompts p
LEFT JOIN current_metrics cm ON cm.root_id = p.id
LEFT JOIN prev_metrics pm ON pm.root_id = p.id
LEFT JOIN (
    SELECT parent_prompt_id, COUNT(*) AS cnt
    FROM tracked_prompts
    WHERE company_id = :company_id AND parent_prompt_id IS NOT NULL AND active = true
    GROUP BY parent_prompt_id
) fc ON fc.parent_prompt_id = p.id
WHERE p.company_id = :company_id 
  AND p.parent_prompt_id IS NULL   -- Only parent prompts
  AND p.active = true
ORDER BY p.created_at DESC

3a. New Repository Method — Prompt-Scoped Responses

async def get_responses_for_prompt_scope(
    self, prompt_id: UUID, days: int = 30
) -> Sequence[DailyRunResponseModel]:
    """Fetch responses for a prompt AND all its fanout children.
    
    Uses: WHERE prompt_id = X OR parent_prompt_id = X
    Leverages: ix_responses_prompt_created + ix_responses_parent_created
    """
    cutoff = datetime.now(timezone.utc) - timedelta(days=days)
    stmt = (
        select(DailyRunResponseModel)
        .where(
            and_(
                or_(
                    DailyRunResponseModel.prompt_id == prompt_id,
                    DailyRunResponseModel.parent_prompt_id == prompt_id,
                ),
                DailyRunResponseModel.created_at >= cutoff,
            )
        )
        .order_by(DailyRunResponseModel.created_at.desc())
    )
    return (await self._session.execute(stmt)).scalars().all()

Scaling Strategy
Why SQL aggregation + Redis cache is the right choice now:

Metric	Current (1 client)	Near-term (50 clients)	Scale limit
Responses/company/month	~6K	~6K each	~300K total
Enriched list query	<50ms	<50ms per tenant	Partitioning at ~10M rows
Redis cache hit rate	~80% (5-min TTL)	~80%	Linear memory growth
When to introduce materialized stats table: If a single company exceeds 500K responses (>2 years of daily 4-engine runs with 200 prompts). At that point, add a prompt_daily_stats table populated by a post-run hook — the API contract stays the same, only the data source changes.

When to introduce partitioning: If daily_run_responses exceeds 10M rows total. Range-partition by created_at (monthly). The cleanup job already clears response_text after 30 days, so old partitions are lightweight.

The key design principle: the API contract is stable regardless of backend implementation. Frontend calls /prompts/enriched and gets the same shape whether it's computed on-the-fly, read from a materialized table, or served from Redis cache.
